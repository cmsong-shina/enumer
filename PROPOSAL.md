
# OpenAPI Spec Generation with oapi-codegen Extension Support

## TL;DR

Add an option to generate OpenAPI spec files from enums, specifically for Go server/client stub generation via oapi-codegen:

Expected output:

```yaml
type: string
enum: [off, horizontal, vertical, all]
x-go-type: state.FanOscillationMode
x-go-type-import:
  path: example.com/enumer-openapi/state
  name: state
```

## Description

OpenAPI is widely used in web development, and oapi-codegen is a tool that generates Go server and client code from OpenAPI specs.

Ideally, the OpenAPI spec itself would serve as the single source of truth, but tooling support for this approach is lacking in the Go ecosystem.

For example, when generating Go enum types with oapi-codegen, they can only be generated as string aliases, and there is no support for generating SQL or GraphQL method code.

As a result, you have to define enums with enumer, then manually handle conversions with the types generated by oapi-codegen. When a new enum value is added, you must update both codebases, run both code generators, and write the conversion code by hand.

This proposal enables enumer to output partial OpenAPI specs from Go code, which the main OpenAPI spec can then reference, helping Go-centric project development.

Two new flags are introduced: `-openapi-out`, which enables OpenAPI output and specifies the output path, and `-openapi-codegen`, which enables oapi-codegen-specific output (`x-go-type-*` extensions that allow using existing package types instead of generating new enum types).

`-openapi-codegen` must be used together with `-openapi-out`.


## Usage Example

Given the following code in `example.com/enumer-openapi/state/fanoscillationmode.go`:

```go
package state

//go:generate enumer -type=FanOscillationMode -transform lower -openapi-out ../path/to/generate/fanOscillationMode.yaml -openapi-codegen
type FanOscillationMode uint16

const (
	Off FanOscillationMode = iota
	Horizontal
	Vertical
	All
)
```

The following OpenAPI spec will be generated:

`path/to/generate/fanOscillationMode.yaml`

```yaml
type: string
enum: [off, horizontal, vertical, all]
x-go-type: state.FanOscillationMode
x-go-type-import:
  path: example.com/enumer-openapi/state
  name: state
```

> The generated enum values follow the `-transform` option (in this case, `lower`).
> `x-go-type-import.path` and `x-go-type-import.name` are obtained via `g.parsePackage()`.

This can be referenced as follows:

`path/to/generate/openapi.yaml`

```yaml
openapi: 3.0.0
paths:
  /airconditioner:
    get:
      operationId: getAirConditionerState
      responses:
        "200":
          description: Device details
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/DeviceState"
components:
  schemas:
    # Reference the spec generated by enumer here.
    FanOscillationMode:
      $ref: "fanOscillationMode.yaml"
    DeviceState:
      type: object
      properties:
        device_id:
          type: string
        FanOscillationMode:
          $ref: "#/components/schemas/FanOscillationMode"
```

You can then generate Go code from the spec using oapi-codegen:

```bash
oapi-codegen -package=openapi -generate types,gin,skip-prune -o path/to/generate/api.go path/to/generate/openapi.yaml
```

`path/to/generate/api.go`

```go
package openapi

import (
    ...
	state "example.com/enumer-openapi/state"
)

type FanOscillationMode = state.FanOscillationMode
type DeviceState struct {
    FanOscillationMode *FanOscillationMode `json:"FanOscillationMode,omitempty"`
    DeviceId           *string             `json:"device_id,omitempty"`
}

// Server code stubs...
```

Result is:

```
├── go.mod
├── path
│   └── to
│       └── generate
│           ├── api.go
│           ├── fanOscillationMode.yaml
│           └── openapi.yaml
└── state
    ├── fanoscillationmode.go
    └── fanoscillationmode_enumer.go
```

## Concerns

-   This proposal introduces a Go dependency into the spec, making it depend on Go code rather than following a pure spec-first approach.

    While this is a concern, projects that use `x-go-type` already have a dependency on Go code, so this is still valuable for Go-centric monorepo project.

-   Currently, enumer generates only a single Go file per type.

    A similar option is `-gqlgen`. GraphQL also has its own schema file, but enumer only generates marshaling methods for it.
    In contrast, this proposal requires generating additional YAML, which has a significant impact on the internal architecture.

    For example, when adding GraphQL support, only a flag and Generator methods needed to be added, using the `Generator`'s single internal buffer.
    This proposal requires a separate buffer. Combined with the multi-type generation issue described below, this becomes even more complex.

    The current proof-of-concept implementation works but is messy poor rubbish. So:

    -   Skips writing OpenAPI at the end of main
    -   Writes files directly inside `Generator.generate()`
        -   Modified `Generator.generateOpenAPIYAML()` to accept type and values
        -   Since it is called while iterating over each type, `Generator.openAPITypes` is no longer needed.
        -   It break `Generator`'s purity and introduce side effect.

-   The current implementation assumes a separate `go generate` comment exists for each type.

    In other words, generating multiple types into a single spec is not supported.

    In the existing implementation, when generating multiple types at once, the file is named after the first type.

    This would likely produce invalid YAML like:

    ```yaml
    type: string
    enum: [off, horizontal, vertical, all]
    x-go-type: state.FanOscillationMode
    x-go-type-import:
      path: example.com/enumer-openapi/state
      name: state
    type: string
    enum: [auto, heat, cool, away, fanonly]
    x-go-type: state.ThermostatMode
    x-go-type-import:
      path: example.com/enumer-openapi/state
      name: state
    ```

-   Switch from string builder to string formatting for better readability and consistency.

-   Support description field, nullability, widely used extensions like `x-enum-*`.

-   Support `oneOf` + `const` pattern enum

    ```yaml
    type: string
    oneOf:
      - const: off
        title: Off
        description: Blabla ...
      - const: horizontal
        title: Horizontal
        description: Blabla ...
      ...
    ```
